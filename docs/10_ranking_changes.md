# 10: 評価データでモデルの順位が変わる理由

## 3つの評価は、使っている画像が異なる

ローカル検証は、配布されたtrain.csvから取り分けた365枚の評価です。
KaggleのPublicとPrivateは、配布されたテスト画像のうち、それぞれの採点対象の部分で評価されます。
どのテスト画像がどちらに含まれるかや、テスト画像の正解は参加者には公開されていません。

同じモデル・同じ予測CSVでも、採点に使う画像が変わるとAUCは変わります。
今回の画像から、以前の「Score 0.93658」という報告がPrivate Scoreを指していたことも確認できました。

## モデルに全画像で共通する順位があるとは限らない

あるモデルが、全種類の葉・背景・病斑の状態に対して他のモデルを上回るとは限りません。
各モデルが付けるクラスごとのスコアの順番は異なります。
評価する正例・負例の組合せが変わると、AUCでの優劣も変わります。
深いモデルを使うことや、学習条件を同じにすることだけで、全評価セットでの順位が一致するわけではありません。

単にクラスの枚数だけでなく、評価対象のどの症例が得意だったかという違いも重要です。
ただし、今回どの特徴を各モデルが使っていたかまでは調べていません。

## 保存した予測だけを使う実演

プロジェクトのフォルダで次を実行できます。Pythonの標準ライブラリだけで集計します。

```bash
python analysis/rank_sensitivity.py --trials 100 --seed 42
```

保存済みの検証用予測を読み、まず全365枚の各クラスAUCが学習時の記録と一致することを確認します。
次に、クラスごとの画像をほぼ半分ずつに分け、同じモデルのまま181枚の組Aと184枚の組Bを評価します。
100通りの分割を作り、各組でのトップを集計します。
分割のたびにモデルを選び直したり、パラメータを更新したりはしません。

今回の結果では、100通りのうち72通りでA・Bのトップが異なりました。
これは評価する画像に順位が依存する実例です。
元の検証画像内での確認であり、新しい画像での汎化性能の推定や、学習し直した結果の安定性の評価は含みません。
また、KaggleのPublic・Privateの正解や画像の所属を再現したものでもありません。

## 少数クラスと検証値の解釈

ローカルの検証ではmultiple_diseasesの正例は18枚です。
このクラスのAUCも、他のクラスと同じ25%の重みで平均されます。
少数の症例でスコアの順番が変わると、平均AUCにも影響します。

さらに、今回の検証画像は最良エポックを選ぶためにも使っています。
その検証スコアは、選んだ後に初めて評価する独立なテストスコアと同じ位置付けではありません。
今回すべてのモデルでローカルのスコアがKaggleより高いことには、分割の違いや選択の影響が考えられますが、原因は特定していません。

## 今回確定したことと、まだ分からないこと

今回のPublicでは50、Privateでは34、ローカルでは18が最良でした。
保存した重みと提出ファイルの対応は確認済みです。

ローカルで50のmultiple_diseasesのAUCが低かったことは事実ですが、
Kaggleでも同じクラスが低かったかどうかは分かりません。
各モデルのテスト用クラス別AUCがないため、集約されたスコアだけから逆転の具体的原因を特定することはできません。

## 次に調べるなら

まずは同じモデルを、別の学習時の乱数で学習し直して、初期化・学習順の影響を調べられます。
分割による影響を調べる場合は、同じ5分割を各モデルで使う層化交差検証が候補になります。
その場合は、各分割で学習からやり直し、検証画像がそのモデルの学習に入らないようにします。
今回の保存済み予測を小分けにする実演より広い範囲の変動を調べられます。

交差検証でも未知のテスト結果との一致は保証されませんが、1回の分割への依存を減らし、平均とばらつきを比較できます。
普段の改善判断には検証結果を使い、Publicの値だけに合わせて条件を選び続けず、Privateは最終確認として扱う方針にします。
